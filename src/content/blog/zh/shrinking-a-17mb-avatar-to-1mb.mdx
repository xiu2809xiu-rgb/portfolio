我用照片生成了一个自己的 3D 模型，骨骼也绑好了，想把它放在这个网站的首屏。文件有 **17 MB**。这不叫首屏资源，这叫关掉标签页的理由。

## 先测量，再优化

第一反应是去压缩网格。那就错了。至于为什么，一条命令就说清楚了：

```bash
npx @gltf-transform/cli inspect avatar.glb
```

| 资源 | 大小 | 分辨率 |
| --- | --- | --- |
| 网格（11,379 个顶点） | 648 KB | — |
| 法线贴图 | 887 KB | 4096 × 4096 |
| 基础色贴图 | 2.83 MB | 4096 × 4096 |
| 金属度-粗糙度贴图 | **12.24 MB** | 4096 × 4096 |

几何数据本来就很小。光是一张 4K、**PNG 格式**的金属度-粗糙度贴图，就占了整个文件的 72%——而且每张 4K 纹理上传到 GPU 之后，大约要占 90 MB 显存。三张加起来就是大约 **268 MB 显存**，只为了一个缩在屏幕一角的角色。

压缩网格顶多省下几百 KB，什么问题都解决不了。

## 不同的贴图，给不同的预算

关键是想明白一点：这三张纹理并不同等重要。基础色是人真正看得见的东西。粗糙度数据属于低频信息，经得起压——高光稍微糊一点，从来没人看得出来。

```javascript
const SLOT_RULES = [
  { match: /basecolor|albedo/i, size: 1024, quality: 84 },
  { match: /normal/i,           size: 1024, quality: 80 },
  { match: /_rm$|roughness/i,   size: 512,  quality: 72 },
];
```

然后缩小尺寸，重新编码成 WebP，再写回去：

```javascript
const out = await sharp(Buffer.from(tex.getImage()), { failOn: 'none' })
  .toColourspace('srgb')
  .resize(rule.size, rule.size, { fit: 'fill' })
  .webp({ quality: rule.quality, effort: 6 })
  .toBuffer();

tex.setImage(new Uint8Array(out)).setMimeType('image/webp');
```

那个 `failOn: 'none'` 可不是摆设。gltf-transform CLI 自带的 `resize` 命令处理这个文件时会崩溃，报的是 libvips 的一个色彩空间断言，所以我最后没有把几条 CLI 命令串起来用，而是自己手写了这一步。

## 结果

| | 优化前 | 优化后 |
| --- | --- | --- |
| 文件大小 | 16.36 MB | **1.24 MB** |
| 基础色贴图 | 2.70 MB | 0.11 MB |
| 金属度-粗糙度贴图 | 11.67 MB | 0.03 MB |
| 动画 | 7 段 | 7 段 |

**体积缩小了 92.4%**，7 段动画一段不少。

这个压缩比乍看不太可信，看一眼纹理图集就明白了：生成器烘焙出来的是大片大片的纯色，这几乎是 WebP 最擅长的情况。换成手绘纹理，效果就另当别论了。

## 比压缩更费时间的那个 bug

模型加载是快了，也渲染出来了——僵在一个标准的 T-pose 上。动画混合器在运行。动画片段都在。可就是一动不动。

原因是我想都没想就写下的一行代码：

```javascript
const model = scene.clone(true); // ← this is the bug
```

`Object3D.clone()` 不会把 `SkinnedMesh` 重新绑定到克隆出来的骨架上。结果克隆体永远停在绑定姿势，动画混合器却还在兴致勃勃地驱动一副没人理会的骨骼。要么改用 `SkeletonUtils.clone()` 来克隆，要么——如果模型只挂载一次——干脆别克隆。

## 想对当初的自己说

先做性能分析，再动手。我差点花一个下午去折腾 Draco 压缩，可网格只占问题的 4%；真正的解法，不过是意识到一张粗糙度贴图用不着 4096 像素宽。
