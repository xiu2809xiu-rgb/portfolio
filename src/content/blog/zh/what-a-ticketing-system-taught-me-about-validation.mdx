在《Web 开发项目》（Web Development Project）这门课上，我做的是 Singink 的客服与工单模块——工单提交表单、管理后台、文件上传，一样不少。我原以为最有意思的会是后台。并不是。是表单。

## 客户端校验是体贴，不是防线

我的第一版靠的是 HTML 属性：

```html
<input name="subject" required minlength="5">
```

这确实有用——不用往服务器跑一趟，就能即时给出反馈。但要绕过它也毫不费力：随便谁打开开发者工具，随便哪个脚本直接向接口发 POST 请求，这些约束就全都形同虚设。

所以同样的规则在服务器上也有一份，那里才是它们真正生效的地方：

```python
subject = request.form.get('subject', '').strip()

if not subject or len(subject) < 5:
    flash('Subject must be at least 5 characters.', 'error')
    return redirect(url_for('tickets.create_ticket'))
```

注意那个 `.strip()` 调用。少了它，5 个空格也算合法的主题。这一点是一位同学帮我发现的，测试方法是对着空格键一通乱按。

## 错误提示也是产品的一部分

我最初的提示，用的是框架自带的那句：“Invalid input.”（输入无效）。怎么个无效法？哪个字段？用户该怎么办？

后来我把提示改成告诉用户下一步该做什么——写“Subject must be at least 5 characters”（主题至少要 5 个字符），而不是“Invalid subject”（主题无效）。结果测试时，填到一半就放弃的人少了，数据上看得出来。这是一次 UX 改动，只是披着报错文案的外衣。

我现在遵循的规则是：错误提示要让人不用猜就能把问题改好。

## 保留用户填过的内容

最让参与测试的人恼火的，不是表单被打回，而是打回的同时，一整段用心写好的描述也没了——就因为主题太短。重新渲染表单时，要把用户填过的内容原样带上。为了执行另一个字段的规则而弄丢别人的心血，这不叫校验，这叫惩罚。

## 边界上校验，边界内信任

有个模式我一再用到，如今写 TypeScript 和写 Python 时都在用：所有检查都在边界上做完，系统内部就可以假定数据是可靠的。只要一个 `Ticket` 对象存在，它的主题就一定合法——否则它根本构造不出来。

这样，校验逻辑就不会散落在每一个碰这份数据的函数里——同一个长度检查写出四个略有出入的版本，就是这么来的。

## 最后的结果

系统做完后，在我们的测试场景里，需要人工处理的客服工作减少了约 60%。这几乎都不是我当初最期待的那个后台的功劳。功劳在那个提交表单：它第一次就把该收的信息收齐、收对，工单一到就能直接处理，不用再回头追问。

最不起眼的那部分，才是最要紧的。
